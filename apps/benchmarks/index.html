How to read these numbers (the honest part)

  1. Vsync caps everything. Browsers align frames to your display refresh (measured above). A median at the cap means “at least this fast” — the real headroom is invisible from JavaScript.
  2. The workloads are not identical — on purpose, and in Three.js's favor. Yura cells run the full pipeline: GPU simulation (attraction + flow noise + swirl), HDR trails, threshold bloom, anamorphic streaks, procedural nebula + starfield, ACES tonemapping. The Three.js cells draw raw additive points with no post-processing.
  3. “Three.js · CPU sim” is the typical implementation, not Three.js at its best. It updates a typed array every frame and re-uploads it — exactly what most tutorials and production sites do. Three.js can go much faster with hand-written GPGPU.
  4. “Three.js · GPU vertex” is Three.js done well — particles animated statelessly in a custom vertex shader, zero per-frame uploads. It is fast, but stateless: it cannot express attraction fields, morphing, or pointer shockwaves. Matching Yura's stateful simulation in Three.js requires a custom GPGPU/compute setup (hundreds of lines). The difference isn't possibility — it's the work required.
  5. Same-machine variance is real. Thermals, battery state, other tabs, and the compositor all move numbers by a few percent. Run the sweep twice before quoting anything.
  6. Method: each cell renders alone into the same 960×540 stage at min(devicePixelRatio, 2); Yura's quality governor is disabled (fixed count, fixed resolution); 1.2 s warm-up, then 3.5 s of requestAnimationFrame deltas → median FPS and p95 frame time; the renderer is disposed and the page cools 0.4 s between cells.
